ISSUE #2: REALTIME UPDATES NOT CONNECTED
================================================================================

Problem:
  The infrastructure for realtime updates exists in SupabaseConfig and
  SupabaseService, but no UI screen actually uses the realtime streams.

  When a leave request is submitted, the LeaveStatusScreen won't update
  unless user manually refreshes.

Current Architecture (Defined but Unused):

  In SupabaseConfig:
    static Stream<Map<String, dynamic>> subscribeToLeaveRequests(
      String companyId
    ) {
      return client
          .from(tableLeave)
          .on(
            RealtimeListenOptions(
              event: '*',
              filter: RealtimeListenOptions.formatFilter({
                'column': 'company_id',
                'value': companyId,
              }),
            ),
            (payload) => payload.newRecord as Map<String, dynamic>,
          )
          .asStream();
    }

  In SupabaseService:
    Stream<LeaveRequest> subscribeToLeaveRequests(String companyId) {
      return SupabaseConfig.subscribeToLeaveRequests(companyId)
          .map((data) => LeaveRequest.fromJson(data));
    }

What's Missing in LeaveStatusScreen:
  - No StreamBuilder implementation
  - No subscription to leave updates
  - No listener for new/updated/deleted leave requests
  - No automatic UI refresh on changes

How Realtime Should Work:
  1. User submits leave request in ApplyLeaveScreen
  2. SupabaseService.applyLeave() inserts into leave_requests table
  3. Supabase triggers realtime event (INSERT event)
  4. LeaveStatusScreen StreamBuilder receives update
  5. List rebuilds with new pending request
  6. No manual refresh needed

Implementation Example:

  class LeaveStatusScreen extends StatefulWidget {
    @override
    State<LeaveStatusScreen> createState() => _LeaveStatusScreenState();
  }

  class _LeaveStatusScreenState extends State<LeaveStatusScreen> {

            return LoadingWidget();
          }

            requests: snapshot.data as List<LeaveRequest>,

        },
      );
    }
  }

  2. Create BehaviorSubject to maintain leave list state

  4. Handle INSERT, UPDATE, DELETE events

ISSUE #3: DATE VALIDATION MISSING
================================================================================

Problem:
  No validation to ensure:
  - Start date is not in the past
  - End date is after start date
  - Dates don't overlap with existing approved leave
  - Sufficient leave balance available

What LeaveRequest Model Currently Does:
  - Stores start_date and end_date
  - No validation methods
  - No constraints in model

What's Missing:

  1. Past Date Validation
     Problem: User could apply for leave on July 1 when today is July 5
     Solution: Check start_date >= today

  2. Date Range Validation
     Problem: User could set end_date before start_date
     Solution: Check end_date > start_date

  3. Overlap Validation
     Problem: User could apply for leave July 1-5, then July 3-8
     Solution: Query existing approved leaves for overlap

  4. Balance Validation
     Problem: User with 2 days casual leave could apply for 5 days
     Solution: Check available_balance >= number_of_days

  5. Weekend Exclusion
     Problem: Leave days calculation includes weekends
     Solution: Count only Monday-Friday in date range

  6. Holiday Exclusion
     Problem: Leave days calculation includes public holidays
     Solution: Query public_holidays table and exclude

Validation Implementation Locations:

  Option A: In Form Widget
    - Real-time validation as user selects dates
    - Show available balance as they select
    - Prevent submission if invalid
    - Best UX

  Option B: In Model Class
    - Add validation methods to LeaveRequest
    - Create LeaveValidator helper class
    - Centralized validation logic

  Option C: In Database Triggers
    - Backend validation prevents invalid inserts
    - Safety net if frontend bypassed
    - Required for data integrity

  Recommended: Both A + C (Frontend UX + Backend Safety)

Example Frontend Validation:

  void onEndDateSelected(DateTime endDate) {
    if (endDate.isBefore(startDate)) {
      showError('End date must be after start date');
      return;
    }

    int businessDays = calculateBusinessDays(startDate, endDate);

    if (businessDays > availableBalance) {
      showError('Insufficient balance. Available: $availableBalance days');
      return;
    }

    setState(() {
      this.endDate = endDate;
      this.numberOfDays = businessDays;
    });
  }

Example Backend Trigger (SQL):

  CREATE OR REPLACE FUNCTION validate_leave_request()
  RETURNS TRIGGER AS $$
  BEGIN
    -- Prevent past date applications
    IF NEW.start_date < CURRENT_DATE THEN
      RAISE EXCEPTION 'Cannot apply for leave in the past';
    END IF;

    -- Prevent end before start
    IF NEW.end_date < NEW.start_date THEN
      RAISE EXCEPTION 'End date must be after start date';
    END IF;

    -- Check for overlapping approved leave
    IF EXISTS (
      SELECT 1 FROM leave_requests
      WHERE employee_id = NEW.employee_id
      AND status = 'approved'
      AND tsrange(start_date, end_date) &&
          tsrange(NEW.start_date, NEW.end_date)
    ) THEN
      RAISE EXCEPTION 'Overlapping approved leave exists';
    END IF;

    RETURN NEW;
  END;
  $$ LANGUAGE plpgsql;

  CREATE TRIGGER check_leave_request
  BEFORE INSERT ON leave_requests
  FOR EACH ROW
  EXECUTE FUNCTION validate_leave_request();

ISSUE #4: LEAVE BALANCE NOT TRACKED
================================================================================

Problem:
  No way to check if employee has sufficient balance before applying leave.
  The leave_balance table doesn't exist in the schema.

Current State:
  - leave_requests table exists
  - Stores individual leave requests
  - No balance tracking per employee per type
  - Cannot query "How many casual leave days does John have left?"

What's Needed:

  1. leave_balance Table
     Purpose: Track annual balance per employee per type

     CREATE TABLE leave_balance (
       id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
       employee_id UUID NOT NULL REFERENCES employees(id),
       company_id UUID NOT NULL REFERENCES companies(id),
       leave_type TEXT NOT NULL,
       fiscal_year INT NOT NULL,
       allocated_days INT NOT NULL,
       used_days INT DEFAULT 0,
       pending_days INT DEFAULT 0,
       carryover_from_previous_year INT DEFAULT 0,
       created_at TIMESTAMP DEFAULT now(),
       updated_at TIMESTAMP DEFAULT now(),
       UNIQUE(employee_id, leave_type, fiscal_year)
     );

  2. public_holidays Table
     Purpose: Define non-working days for leave calculation

     CREATE TABLE public_holidays (
       id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
       company_id UUID NOT NULL REFERENCES companies(id),
       holiday_name TEXT NOT NULL,
       holiday_date DATE NOT NULL,
       is_optional BOOLEAN DEFAULT false,
       created_at TIMESTAMP DEFAULT now(),
       UNIQUE(company_id, holiday_date)
     );

  3. leave_policies Table
     Purpose: Define allocation rules per company

     CREATE TABLE leave_policies (
       id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
       company_id UUID NOT NULL REFERENCES companies(id),
       leave_type TEXT NOT NULL,
       annual_allocation INT NOT NULL,
       can_carryover BOOLEAN DEFAULT false,
       max_carryover_days INT DEFAULT 0,
       fiscal_year_start_month INT DEFAULT 1,
       created_at TIMESTAMP DEFAULT now(),
       UNIQUE(company_id, leave_type)
     );

  4. RPC Function: Calculate Balance

     CREATE OR REPLACE FUNCTION get_leave_balance(
       p_employee_id UUID,
       p_leave_type TEXT
     ) RETURNS INT AS $$
     DECLARE
       v_allocated INT;
       v_used INT;
       v_pending INT;
       v_balance INT;
     BEGIN
       -- Get allocated balance
       SELECT allocated_days INTO v_allocated
       FROM leave_balance
       WHERE employee_id = p_employee_id
       AND leave_type = p_leave_type
       AND fiscal_year = EXTRACT(YEAR FROM CURRENT_DATE);

       -- Calculate used days
       SELECT COALESCE(SUM(number_of_days), 0) INTO v_used
       FROM leave_requests
       WHERE employee_id = p_employee_id
       AND leave_type = p_leave_type
       AND status = 'approved'
       AND EXTRACT(YEAR FROM start_date) = EXTRACT(YEAR FROM CURRENT_DATE);

       -- Calculate pending days
       SELECT COALESCE(SUM(number_of_days), 0) INTO v_pending
       FROM leave_requests
       WHERE employee_id = p_employee_id
       AND leave_type = p_leave_type
       AND status = 'pending'
       AND EXTRACT(YEAR FROM start_date) = EXTRACT(YEAR FROM CURRENT_DATE);

       v_balance := v_allocated - v_used - v_pending;
       RETURN v_balance;
     END;
     $$ LANGUAGE plpgsql;

  5. Service Method: Fetch Balance

     Future<int> getLeaveBalance(
       String employeeId,
       String leaveType,
     ) async {
       try {
         final result = await client.rpc(
           'get_leave_balance',
           params: {
             'p_employee_id': employeeId,
             'p_leave_type': leaveType,
           },
         );
         return result as int;
       } catch (e) {
         throw Exception('Failed to calculate balance: $e');
       }
     }
